# AUDIT — Migrations/RLS (agent audit-db) — LIVE-VERIFIED

## SYSTEM MAP
87 tables in public, all RLS enabled (87/87 relrowsecurity=t). 4 deny-all (service-only, correct): afip_ta_cache, padron_cache, rate_limit_buckets, search_index_state. **16 tables USING(true) SELECT to authenticated.** Sales invoices/receipts/transactions/checks role-gated (owner/admin/finance); purchase_invoices NOT (open) — asymmetry.
14 views + 1 matview. 10 views security_invoker=on; **5 lack it** (definer): v_attendance_records_resolved, v_employee_vacation_balances, v_file_attachments_resolved, v_payroll_entries_resolved, v_payroll_entries_with_payments. Matview search_index granted to anon+authenticated.
66 SECURITY DEFINER functions; ALL have set search_path=public (no search-path hole). But Supabase default privileges grant EXECUTE to anon+authenticated on every public function; 60/66 exposed. Only 6 (*_opening_balance) carry internal user_has_role guard.
Triggers: journal-generation, delete-guards, immutability, FTS dirty-flag, timestamps, owner-minimum. Journal triggers swallow P0002 (missing COA account) as raise warning — parent write survives, entry silently skipped.

## FINDINGS

Any authenticated user (driver/warehouse) calls PostgREST rpc('create_journal_entry',{...balanced lines...}) → runs as owner, bypasses RLS, inserts forged GL entry → pollutes Libro IVA/balance/Mayor. **CONFIRMED via LIVE EXPLOIT** (inserted row+lines, returned UUID; only unbalanced payload rejected by balance constraint). accounting:write matrix fully bypassed. Fix: add user_has_role guard at top (as opening-balance RPCs do), OR revoke from authenticated + fix default-privilege gap.
[CRITICAL][broken-access] `20260516160200_files_storage_bucket.sql:36-68` — files bucket SELECT and DELETE storage policies gate on exists(select 1 from public.files...), but files RLS is USING(true) → subquery true for every authenticated user. employee_documents.attachment_file_id→files(id); employee docs (carnet, libreta sanitaria) live in files bucket. employee_documents table RLS is HR-only but defeated: any authenticated user reads files (USING true) → bucket_path → downloads PDF via files_storage_select and DELETES via files_storage_delete. ## DESIGN TENSIONS
1. Service-role-bypasses-RLS + definer RPCs granted to authenticated = double surface. Stated model "server actions use service-role; RLS is defense-in-depth for anon surface" undercut because create_journal_entry et al. grant to authenticated → PostgREST can invoke privileged WRITES directly. Inconsistent (opening-balance RPCs guard; journal RPCs don't).
2. files as shared bucket with single USING(true) registry table cannot express per-entity confidentiality. Employee-doc + purchase-invoice PDFs share one bucket + one blanket policy.
3. Round-2/3 post-audit migrations fixed most-visible tables (journal, sales invoices) not their mirror (purchases, files, buckets). Audit was table-name-driven not surface-driven.

## EXPECTATION GAPS
- "Every table gets RLS" honored (87/87) → false confidence: RLS-enabled ≠ RLS-effective. 16 tables USING(true), two buckets holding private docs effectively public-to-authenticated.
- Authors repeatedly wrote revoke all...from public believing it locks to service_role. It doesn't on Supabase.
- search_path=public uniformly set (good) — classic definer hole absent; exposure is purely EXECUTE-grant + missing-guard.
