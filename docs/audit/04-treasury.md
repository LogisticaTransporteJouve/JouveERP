# AUDIT — treasury/money-movement (agent audit-treasury)

## SYSTEM MAP
Balance model: DERIVED, never stored. accounts.opening_balance + Σ signed transactions (income/transfer_in=+, expense/transfer_out=−), aggregated in JS by treasury-actions.ts + cash-flow-actions.ts. Parallel journal ledger computes accounting balances independently (get_account_balances, L.5).
Flows: Receipt (create_receipt/update_receipt RPCs, last 20260510204115): header+payment_lines+allocations+retentions+one income tx per line + auto-created checks row when line hits checks/echeq account. Cancel=status UPDATE; trigger handle_receipt_cancellation deletes linked transactions only.
Payment order (create/update_payment_order, last 20260514215801/20260516102448): lines account|endorse_check (flips en_cartera→endosado)|issue_check (inserts issued_checks); one expense tx per line at OP creation. Cancel trigger reverts endorsed checks, cancels emitted issued checks, deletes all OP transactions.
Third-party checks: RPCs deposit_check (transfer pair cartera→bank), credit_check, reject_check. Issued checks: informational; free status transitions from action layer; journal trigger only fires from emitted.
Aging: v_aging_documents/v_supplier_aging_documents compute open_amount=imp_total−allocations; buckets keyed to invoice date, evaluated at SELECT.
Crons: bcra-exchange-rate (business days 11:00 ART insert-if-absent), aging-weekly-summary (Mondays email top-50).
Invariants: Σpayment_lines+retentions=total (RPC+Zod); Σallocations≤doc total (RPC+Zod); per-invoice applied≤outstanding NOWHERE; allocation invoice belongs to header's client/supplier NOWHERE; check spent once (status precondition, no row lock + partial UNIQUE on endorsed_check_id; deposit path unguarded); tx currency=account currency NOWHERE; numbering unique (index; suggestion=unlocked MAX+1).

## DESIGN TENSIONS
1. Two ledgers, one reality — caja (transactions) books deferred issued checks as bank expense at EMISSION; journal books bank credit at CASHING. Every lifecycle event must reconcile both; several fix only one (findings 4,7, issued-check rejection).
2. Mutable documents + delete/reinsert RPCs vs trigger choreography — receipts/OPs editable+cancelable, each edit rewrites children wholesale; correctness depends on ever-growing compensating triggers. Findings 5,6,8 are leaks. Append-only (cancel=reversal) eliminates class.
3. Derived balances with app-side math — correct balances require reading every transaction in JS on every dashboard load; already broken at 1000-row cap. Materialize per-account running balances or push aggregation to SQL.

## EXPECTATION GAPS
- House convention getServiceClient; entire treasury uses RLS user client + security invoker RPCs (safer but systematic deviation).
- Sales NCs wholly excluded from client aging while purchase NCs net against origin — asymmetric.
- recurring_payments.next_due_date never advanced by anything (no generation cron) — projection-only though model implies scheduled execution.
- Payment orders have no draft→confirmed→paid lifecycle; money moves at creation (issued).
- PaymentOrderCreateSchema accepts endorse_check line amount from client, RPC overwrites w/ check amount — sum validation fails confusingly if UI amount drifts.
