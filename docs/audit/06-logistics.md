## SYSTEM MAP
Tables (all RLS'd, money/km numeric never float): drivers, vehicles, trips (RLS owner/admin/operations + driver self via drivers.user_id), fuel_loads, maintenance_records (cascade-delete from vehicles), fleet_documents (XOR owner check, notified_at cooldown), shipments + shipment_status_history (append-only via RLS insert-only), warehouses/products/pallets (RLS owner/admin/warehouse), storage_tariffs (RLS owner/admin/finance), storage_billing_runs (+applied_tariffs jsonb snapshot).

Invariants: no double storage billing APP-LEVEL only (overlapsBilled, no DB exclusion constraint); no double freight billing APP-LEVEL only (invoice_id null-check); shipment state machine UI only (server accepts any→any); pallet exit≥entry DB check; tariff/handling≥0 DB checks; patente unique, one user↔one driver DB uniques; driver/vehicle non-double-booking NOWHERE; tariff-per-period via pure TS pickTariff (one tariff per whole period).

## DESIGN TENSIONS
1. RLS client vs service client — logistics runs every action through RLS client → authorization enforced twice (userCan + policies) w/ different role sets. Any cross-domain feature (storage billing spans finance perms + warehouse data) breaks silently — finding #3 is first casualty.
2. Snapshot-after vs compute-live — applied_tariffs makes runs self-describing, but invoice computes from live tariffs at emit time — preview user approved + amount emitted diverge if tariff changes between; snapshot faithfully records surprise.
3. UI-owned state machines — shipments/trips lifecycles only in component maps. Every new client of server actions (AI tools) re-inherits any→any hole.
